# Isolated Linux candidate builds

`deploy/build-candidate.sh` produces a release archive; it does not deploy, activate, restart, or read credentials from an application environment. Use it when the application host lacks build capacity. Linux dependencies must be built on the same CPU architecture and a compatible Linux distribution/Node version as the destination.

The retired host `54.39.230.141` is a temporary builder, not a staging deployment target. On 10 November 2026 it had approximately 3.3 GB available RAM and 4 GB swap, Node 22.23.3 under `/opt/ps-booking-node/bin`, and no running application services. Recheck capacity, free disk, and the backup schedule before each build; do not overlap a backup or restore. Backups currently begin at 02:07 UTC. The application host remains `188.245.178.173`.

## Prepare explicit public input

1. Finish verification and commit the exact source. Generate a clean archive from the repository root: `git archive --format=tar.gz --output=<SHA>.tar.gz <SHA>`. Do not archive a working directory or add a prefix; the helper validates the Git commit header and refuses links, private environment files, generated dependencies, and path traversal.
2. Prepare `<SHA>.public.env` separately, containing only explicitly reviewed `NEXT_PUBLIC_*`, `CONTENT_MODE`, and `PROPHOTO_SITE` entries. Set the intended staging origin, staging public Supabase settings, and `NEXT_PUBLIC_ACADEMY_DESIGN=studio`. Public values are embedded in the browser bundle. Never supply a runtime environment file, database URL, service-role key, or provider credential. Blank lines/comments and literal matching quotes are accepted; shell substitution and variable interpolation are not performed.
3. Transfer these two files to `/srv/prophotoacademy-build/incoming/`. The base, incoming directory, and input files must be root-owned and not writable by group/others; paths must contain no symlinks. Suggested modes: directories `0755`, input files `0600`. Keep output directories root-owned. The `prophotoacademy-staging` account must already exist.
4. Install the reviewed helper as a root-owned executable, then run `sudo /path/to/build-candidate.sh <SHA>`. Do not modify a candidate after submission. Existing candidates and artifacts are refused; failed trees remain available for inspection, and removal requires a separately reviewed, exact path.

The transient `academy-candidate-<SHA>` unit runs as the existing staging account. It can write only `/srv/prophotoacademy-build/<SHA>` plus its private temporary directory. It uses an empty inherited environment, dedicated package caches, no privilege escalation, protected home/system directories, and inaccessible old application/configuration/backup paths. Limits are 2,200 MB RAM, 1,536 MB swap, one CPU, nice level 15, and 90 minutes. These limits reduce interference; they do not replace a capacity and backup-window check. Package installation still needs outbound registry access.

## Transfer and activate separately

The result is `/srv/prophotoacademy-build/output/<SHA>.tar.gz` with a SHA-256 record for its source archive, public configuration, and output. The Linux payload contains `.next`, `public`, `node_modules`, package/lock/config files, public fallback content, and `deploy/deliver-email.mjs`. The email timer's `ExecStart` invokes that worker from the active release, so the helper requires it in the source archive and verifies that it remains a nonempty regular file before packaging. The archive preserves pnpm symlinks and omits caches, `.git`, `.data`, and environment files. Treat generated `.next` contents as executable code and review the supplied commit before running the helper.

Copy and verify the output checksum on the application host. Extract it into a new, inactive staging release directory with the staging account's ownership, leaving runtime configuration on that host. Verify the expected public build configuration, `BUILD_ID`, and email worker, then follow [staging isolation and activation](STAGING_ISOLATION.md). The candidate helper deliberately has no activation or health-check shortcut. After successful activation and browser smoke checks, retain the active release and one previous verified release using the documented [deployment cleanup](PRODUCTION_DEPLOYMENT.md). Builder candidates and transfer artifacts are separate from application releases and require their own explicit cleanup.
